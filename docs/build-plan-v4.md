# תוכנית בנייה v4 – מערכת אחת במקום iForms + Make + Google Sheets (לביצוע על ידי Sonnet)

> **זה המסמך הפעיל מ-19.10.2026.** הוא מחליף את `builder-plan.md` כמוקד הנוכחי. `build-plan-v3.md` ו-`builder-plan.md` נשארים כרקע (החלטות סגורות, מודל נתונים, מה כבר בוצע). במקרה של סתירה – מסמך זה קובע, ואחריו `CLAUDE.md` והקוד הקיים.
> **הרקע:** סקירת הפערים מ-19.10 (בפרויקט: `claude/סקירת-פערים-iForms-Make-ומה-לבנות.md`; המסמך המלא ב-Claude Docs). הסקירה הראתה: iForms נותן חתימה על מסמך; Make והגיליון הוסיפו מעליו בקשה, נתונים, תיוק, שכר ומעקב. המנוע שלנו כבר מכסה את רוב זה. התוכנית כאן סוגרת את מה שחסר, בסדר שמאפשר להעביר תרחיש אחד מקצה לקצה ואז להחליף את הגיליון.
> **לפני כל עבודה:** `CLAUDE.md`, `docs/HANDOFF.md`, ואז המשימה הבאה כאן בלבד.

## 0. כללי עבודה (גוברים על הכול)

1. **משימה אחת = ענף אחד = PR אחד. לא ממזגים.** אחרי CI ירוק מדווחים לישראל: שם ענף, מספר PR, מה נבנה, מה לא נבדק, מה צריך ממנו. מיזוג רק כשישראל כותב "מזג".
2. **לא נוגעים במסד הנתונים של הייצור ביד.** שינוי סכמה = שינוי ב-`src/db/schema.ts` בלבד; `db-generate` יוצר את ה-SQL ב-main, וה-build של Vercel מחיל אותו על הייצור (`AUTO_MIGRATE=1`, `scripts/migrate.ts`). על dev מחילים את אותו SQL (Neon MCP) כדי שהבדיקות ירוצו.
3. **לא מחליטים על מה שלא כתוב כאן.** שאלה פתוחה → עוצרים ושואלים. הנחות בסעיף 2 מותר לממש כמו שהן כתובות.
4. **משימת UI → מריצים את הסקיל `ui-ux-pro-max` לפני, ומאמצים את ההמלצות** (הכללים ב-`CLAUDE.md` עדיין גוברים: עברית, RTL, logical utilities, טוקנים).
5. **TDD ללוגיקה** (vitest ב-`tests/`), Playwright לתרחיש, ו"בוצע כאשר" של כל משימה נבדק לפני הדיווח.
6. **אבטחת תוכן היא בשרת, לא בתצוגה.** שדה פנימי ותפקיד מעקב נאכפים ב-`validateAnswers`, ב-`src/server/guards.ts` ובנתיבי ה-API, ולא רק ב-JSX.
7. נתקעים 3 פעמים על אותה שגיאה → עוצרים ומדווחים.

## 3. שינויי סכמה (PR אחד, משימה 1)

```
users:            email → nullable (עדיין unique כשקיים); + login text unique not null (ברירת מחדל: המייל הקיים)
                  grants + { track, followUp }
employees (new):  id, idNumber text unique, name, email?, phone?, createdAt/updatedAt
employee_organizations (new): employeeId, organizationId, projectId?   (pk: employeeId+organizationId)
requests:         + employeeId uuid → employees (nullable; ממולא ביצירה לפי ת"ז)
                  + followUp jsonb  { [key]: { at, byUserId } }
package_templates: + expiryRule jsonb  { kind: "days", days } | { kind: "dayOfNextMonth", day, dateFieldId } | { kind: "none" }
                   + completionRecipients jsonb  [{ name, email }]   (מקבלים את מייל הסיום + ה-PDF)
                   + followUpStatuses jsonb  [{ key, label }]
                   + remindersEnabled boolean default true
FormField (schema.ts, לא DB): + internal?: boolean
organizations:    + weeklyDigest boolean default true
```

## 4. משימות

לכל משימה: **קבצים**, **בוצע כאשר** (בדיק), **בדיקות**. המספור הוא סדר הביצוע. ענף: `v4-<n>-<slug>`.

### שלב א – בסיס · ~3 ימים

**1. סכמה ומיגרציה. ✅ בוצע (PR #156).** קבצים: `src/db/schema.ts`, `src/lib/forms/schema.ts` (`internal`), `src/lib/auth/permissions.ts` (`track`, `followUp` ב-`GRANT_KEYS` + תוויות), `drizzle/`. כל סעיף 3. ל-`users.login` ברירת מחדל = המייל הקיים (מיגרציה `update users set login = email`). **בוצע כאשר:** typecheck ירוק; המיגרציה נוצרה ב-CI והוחלה על dev; `normalizeGrants` מחזיר את שני המפתחות החדשים. **בדיקות:** `tests/permissions.test.ts` – `hasGrant(u,"track")`.

**2. ערכת בדיקה "שינוי תנאים" בריפו. ✅ בוצע (PR #156).** קבצים: `tests/fixtures/package-terms-change.ts` (FormDefinition של טופס הבקשה עם 19 השדות של iForms – `fname, lname, id_number, mobile, email_address, salary, salary_interval, travels, job_scope, work_time, start_work_date, boss_name, company_name, Organization_name, job_main_description, additional_conditions, contract_number, manager` + שדות פנימיים `cost_center`, `department`; מסלול: requester → employee → approver מ-`manager` → payroll), `tests/fixtures/terms-change.pdf` (PDF ריק של 2 עמודים שנוצר ב-pdf-lib, בלי נתונים אישיים), `scripts/seed.ts` (מוסיף את הערכה ל-dev). **בוצע כאשר:** `pnpm seed` יוצר את הערכה; Playwright `tests/e2e/terms-change.spec.ts` פותח בקשה, העובד ממלא, המאשר מאשר, חשבות מסיימת, ו-PDF נוצר. **בדיקות:** ה-e2e הזה הוא הבסיס לכל המשימות הבאות.

**3. ריצת עשן בייצור (ישראל + Sonnet).** Sonnet מכין צ'קליסט ב-`docs/smoke-v4.md`: בקשה מערכה קיימת → עובד → מאשר → חשבות → PDF → מייל. ישראל מריץ בפרודקשן ומדווח. **בוצע כאשר:** הצ'קליסט מסומן, וכל כשל נרשם כמשימה חדשה לפני המשך.

### שלב ב – "שינוי תנאים" מקצה לקצה · ~שבוע

**4. שדות פנימיים – אכיפה. ✅ בוצע (PR #156).** קבצים: `src/lib/forms/merge.ts` (`mergedDefinitionForStep` משמיט `internal` לכל תפקיד שאינו requester), `src/lib/forms/validate.ts` (תשובה לשדה `internal` מתפקיד אחר → שגיאה; לא נכנסת ל-`cleaned`), `src/lib/forms/pdf-mapping.ts` / `src/server/finalize.ts` (חותמת של שדה `internal` לא מצוירת), `src/lib/pdf/summary.ts` (לא בסיכום), `src/lib/notifications/*` (לא בגוף מייל), `src/app/s/[token]/*` (לא בכרטיס "פרטים שמולאו"), `src/lib/export/rows.ts` (כן), `src/app/admin/requests/[id]/*` (מוצג בכרטיס "פנימי" לצוות). בבונה: מתג "שדה פנימי (לצוות בלבד)" בהגדרות השדה, רק כש-`filledBy = requester`. **בוצע כאשר:** `tests/internal-fields.test.ts`: merge משמיט, validate דוחה, stamp מדלג, export כולל; e2e: `cost_center` לא מופיע בדף של העובד ולא ב-PDF, כן בייצוא. **בדיקות:** vitest + e2e מספר 2.

**5. כלל תוקף לערכה. ✅ בוצע (PR #156).** קבצים: `src/lib/requests/expiry.ts` (טהור: `expiryFor(rule, answers, sentAt) → Date | null`, "יום N בחודש הבא" לפי Asia/Jerusalem, עם N שגדול מאורך החודש → היום האחרון), `src/server/requests-store.ts` (`createRequest`/`sendRequest` משתמשים בכלל כשאין `expiresAt` מפורש), עורך הערכה (`src/app/admin/packages/[id]/*`: בחירה בין 3 הסוגים + שדה תאריך מרשימת שדות התאריך של הטפסים), `expireOverdue` – בקשה ללא תוקף לא פגה. **בוצע כאשר:** בדיקות: 15.11 + "4 בחודש הבא" → 4.12; 31.1 + "31" → 28/29.2; `none` → null; e2e: הערכה עם הכלל, הבקשה מציגה את התוקף הנכון. **בדיקות:** vitest.

**6. נמעני סיום לערכה + PDF מצורף. ✅ בוצע (PR #156).** קבצים: `src/server/after.ts` / `requests-store.ts` (אחרי `finalizeRequest`: מייל `completed` לכל `completionRecipients` עם ה-PDFים הסופיים מצורפים; Resend תומך ב-attachments), `src/server/notifications.ts` (תמיכה בקבצים מצורפים; עד 10MB סה"כ, מעבר לזה – קישורים), עורך הערכה (רשימת נמענים שם+מייל). **בוצע כאשר:** בדיקת יחידה: רשימת ההודעות אחרי סיום כוללת את הנמענים הקבועים פעם אחת כל אחד (בלי כפילות עם המבקש); בייצור מייל אחד לישראל באישורו. **בדיקות:** vitest.

**7. תזכורות עד חתימה + כיבוי לערכה. ✅ בוצע (PR #156).** קבצים: `src/lib/workflow/reminders.ts` (`maxCount: 0` = ללא תקרה), `reminder-policy.ts` (ברירת מחדל מסעיף 2), `packages` (`remindersEnabled`), `src/server/reminders.ts`. **בוצע כאשר:** בדיקה: 10 ימים בלי חתימה → 3 תזכורות; ערכה כבויה → 0. **בדיקות:** vitest.

**8. בניית ערכת "שינוי תנאים" בייצור (ישראל).** העלאת ה-PDF האמיתי, זיהוי שדות, סימון השדות הפנימיים, מסלול, תוקף, נמענים. Sonnet לא עושה את זה; אם חסר משהו בבונה כדי לעשות זאת – משימה חדשה.

**תנאי סיום לשלב ב:** בקשת "שינוי תנאים" אחת אמיתית עברה בייצור במקביל ל-Make, וחשבות קיבלה את ה-PDF במייל.
