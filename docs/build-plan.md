# תוכנית בנייה – מערכת טפסים, חתימות ודשבורד קליטה/סיום העסקה

> **למי המסמך מיועד:** למודל שמבצע את הבנייה (כולל Sonnet) ולישראל. כל החלטה כאן כבר סגורה. מה שלא כתוב כאן לא מחליטים לבד: עוצרים ושואלים את ישראל.
> **מקורות אמת:** (1) מסמך הפרויקט `claude/מיפוי-מערכת-קליטה-קיימת.md` – איך המערכת הקיימת עובדת. (2) מסמך האפיון "אפיון מערכת טפסים וחתימה דיגיטלית" (Claude Doc) – מודל נתונים, מסכים ותהליכים. אם יש סתירה בין המסמכים לתוכנית הזאת, התוכנית קובעת לגבי טכנולוגיה וסדר עבודה, והאפיון קובע לגבי התנהגות עסקית.

---

## 0. כללי עבודה (חובה בכל שלב)

1. **שלב אחד בכל פעם.** לא מתחילים שלב לפני שכל "תנאי הסיום" של הקודם עברו.
2. **בתחילת כל שלב:** לקרוא את הסעיף שלו כאן, ואז להשתמש ב-skill `superpowers:writing-plans` (אם מותקן) כדי לפרק אותו למשימות של 2–5 דקות. בסוף שלב: `superpowers:requesting-code-review`.
3. **בדיקות קודם (TDD)** לכל לוגיקה: ולידציות, מעברי סטטוס, bidi, ייצוא Priority.
4. **אין סודות בקוד.** כל מפתח ב-Vercel env / `.env.local` (שלא נכנס ל-git).
5. **עברית ו-RTL:** כל UI ב-`dir="rtl"`, רק Tailwind logical (`ms- me- ps- pe- start- end-`), אסור `ml- mr- pl- pr- left- right-`. להיעזר ב-skills `hebrew-first` ו-`ui-ux-pro-max`.
6. **commit קטן** בסוף כל משימה, הודעה באנגלית, ענף `main` רק דרך PR אחרי ש-CI ירוק.
7. **כשנתקעים פעמיים על אותה שגיאה:** `superpowers:systematic-debugging`. אחרי 3 ניסיונות כושלים – לעצור ולדווח לישראל מה נוסה.
8. **לא נוגעים במערכת הקיימת** (iForms, Make, Sheets) עד שלב 6. קריאה מותרת, כתיבה אסורה.

## 3. שלבים

### שלב 1 – שלד + ניסוי עברית ב-PDF (הסיכון הגדול) · ~שבוע

**משימות**
1. `create-next-app` + shadcn/ui + Tailwind v4 RTL + Heebo. דף בית ריק בעברית.
2. Drizzle מחובר ל-Neon (ענף `dev`), migration ראשונה עם טבלת `health`.
3. GitHub Actions: lint, typecheck, vitest. חיבור ל-Vercel (Preview לכל PR).
4. מודול `lib/pdf/hebrew.ts` עם פונקציה:
   `drawHebrew(page, text, { x, y, width, size, align: 'right'|'left'|'center', font })`
   – פיצול ל-runs לפי `bidi-js`, סידור ויזואלי, ציור run אחרי run מימין לשמאל.
5. **30 מקרי בדיקה** בקובץ `tests/pdf/hebrew-cases.ts`, לפחות: שם עברי; "רחוב הרצל 12"; "ת.ד. 123"; ת"ז 9 ספרות; תאריך 01/09/2026; "דירה 4, קומה 2"; סוגריים "(בפועל)"; אנגלית בתוך עברית "Gmail של העובד"; מייל; טלפון 050-1234567; סכום ₪1,234.50; מספר חשבון 12-345-678901; שורה ריקה; טקסט ארוך שעוטף.
6. בדיקות: (א) snapshot ויזואלי – רינדור עמוד ל-PNG והשוואה ל-golden; (ב) הגולדן נבדק בעין ע"י ישראל פעם אחת.

**תנאי סיום**
- [ ] Preview deployment עובד ב-Vercel
- [ ] כל 30 המקרים נראים נכון (ישראל אישר את ה-golden)
- [ ] CI ירוק

**אם הניסוי נכשל אחרי 5 ימי עבודה:** לא ממשיכים לנסות. עוצרים ומציגים לישראל חלופה: רינדור HTML→PDF עם Chromium (Playwright/Browserless) על גבי תמונת הרקע של הטופס.

### שלב 2 – מודל נתונים + דשבורד בסיסי · ~שבוע

1. לממש את מודל הנתונים מהאפיון (14 הטבלאות) ב-Drizzle, כולל: `organizations`, `users`(+תפקיד), `employees`, `requests`, `packages`, `documents`, `form_templates`(JSON SurveyJS + גרסה), `pdf_templates`(+field-map), `signing_steps`, `audit_events`, `cost_centers`(3 רמות), `banks`, `bank_branches`, `settings`.
2. Seed: 4 הארגונים (מספרי עמותה מהמיפוי), מרכזי הרווח מגיליון "מעקב עובדים", מנהלים מאשרים.
3. Auth.js + Google; הרשאות לפי תפקיד: `admin`, `payroll`, `approver`, `org_office` (רואה רק את הארגון שלו).
4. דשבורד: טבלת בקשות עם סינון לפי ארגון/סטטוס/תאריך, חיפוש לפי שם/ת"ז, דף פרטי בקשה עם ציר זמן מ-`audit_events`.
5. מכונת הסטטוסים כפונקציה טהורה `nextStatus(current, event)` עם בדיקות לכל מעבר מותר ואסור. הסטטוסים לפי האפיון.

**תנאי סיום:** משתמש `org_office` לא רואה ארגון אחר (בדיקת E2E); כל מעברי הסטטוס מכוסים בבדיקות.

### שלב 3 – טופס בקשה של מנהל + טופס 101 לעובד · ~2 שבועות

1. טופס בקשת העסקה (מחליף את Google Form "שאלון העסקה") ב-SurveyJS, כולל ההסתעפות לפי מחלקה ומרכזי רווח 1–3 מתוך `cost_centers`.
2. טופס 101 ב-SurveyJS: 10 עמודים (סעיפים א'–י'), `paneldynamic` לילדים, `visibleIf` לתנאים. ולידציות: ת"ז (ספרת ביקורת), טלפון ישראלי, מיקוד, תאריכים.
3. טופסי עובד נוספים לפי התבניות: פרטי בנק (combobox בנקים/סניפים מטבלה מקומית), חוזה (תצוגה + הסכמה).
4. שמירת טיוטה אוטומטית (העובד יכול לחזור בקישור).
5. מובייל קודם: בדיקת Playwright על iPhone 13 ו-Pixel 7.

**תנאי סיום:** ישראל ממלא 101 מלא בנייד בלי תקלות; כל הוולידציות עם בדיקות.

### שלב 4 – חבילת חתימה ושרשרת חותמים · ~2 שבועות

1. `field-map.json` לכל תבנית PDF (מיקום כל שדה). כלי עזר פנימי קטן לסימון מיקומים על PDF.js.
2. יצירת חבילה: אוסף מסמכים לפי סוג התרחיש (עובד רגיל/זמני/שינוי תנאים/סיום/הוספת משרה/רכב/161) – לפי טבלת השרשראות במסמך המיפוי.
3. `signing_steps`: שלב נפתח רק אחרי שהקודם `signed`. token אקראי (hash ב-DB), תוקף 14 יום, OTP במייל לפני חתימה.
4. בכל חתימה: ציור החתימה על ה-PDF, SHA-256 של הקובץ, רישום ב-`audit_events` (IP, user-agent, זמן, hash לפני/אחרי).
5. בסיום השרשרת: PDF מאוחד + עמוד "תעודת השלמה" (כל האירועים וה-hashes), נעילה, שמירה ב-Blob, webhook ל-Make להעתקה ל-Drive (אותה היררכיית תיקיות ושם קובץ כמו היום).
6. מיילים (Resend): הזמנה לחתימה, תזכורת, "נחתם" למי שמילא את הבקשה, "נדחה" עם סיבה.

**תנאי סיום:** תרחיש "עובד רגיל" עובר מקצה לקצה ב-E2E: בקשה → עובד ממלא וחותם → מאשר → חשבות שכר → PDF בארכיון + קובץ ב-Drive.

### שלב 5 – תזכורות, Priority, סיום העסקה · ~1–2 שבועות

1. Vercel Cron: תזכורות לפי לוח הימים הקיים (קליטה: 2,11,14,19,21,29,31; סיום: 1,3,12,17,21,29), לנמענים לפי ארגון.
2. ייצוא Priority: מסך "ייצוא" שמפיק קובץ לפי המיפוי ("לייבוא ללא שינוי"/"מיפוי"/"Y"/"לא לייבוא"), סימון שורות שיוצאו. בדיקות יחידה לכל עמודה ממופה.
3. תהליך סיום העסקה (כולל הודעה למנהל אחרי "נחתם" – **הבאג הקיים בתרחיש 1527209 לא משוכפל**).

**תנאי סיום:** קובץ ייצוא שמשווים מול ייצוא אמיתי מהמערכת הישנה לאותו עובד – זהה.

### שלב 6 – מעבר (Cutover) · ~שבוע

1. ייבוא נתונים היסטוריים מ-Sheets (עובדים פעילים, בקשות פתוחות) – סקריפט חד-פעמי עם dry-run.
2. הרצה מקבילה שבועיים בארגון אחד (מומלץ: פנימה), ואז כל השאר.
3. רק אחרי אישור ישראל: כיבוי תרחישי Make הרלוונטיים וכפתור ה-Apps Script.
